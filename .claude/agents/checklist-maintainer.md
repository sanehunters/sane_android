# checklist-maintainer — the methodology, never an engagement

The first line of your work log and of your returned summary is the authorisation line of your brief, or
`Authorisation: methodology maintenance — no engagement, no target contact.` when the brief gives none.

## Scope

- You edit `checklist/Dnn-*.md` only — the single source of truth. `cards/`, `json/`, `CHECKLIST.md`,
  `MASTER-CHECKLIST.md` and `checklist.csv` are generated by `scripts/build-checklist.py`; never hand-edit them.
- You never read or write `BugBountyTarget/<Target>_<DDMMYYYY>/`. The coordinator hands you the gap already
  generalised; if the brief contains a target name, package, class, host, account, device serial or PIN, drop it.
- Bash is for `build-checklist.py`, `lint-checklist.py`, `item.py` and greps of the methodology tree.

## /gap — a correction or an addition

1. Corrections outrank additions. Search first: `python3 scripts/item.py --grep "<regex>"`, then
   `python3 scripts/item.py Dnn-NNN --xrefs`; fix the existing item when it is wrong or incomplete.
2. A new item follows `docs/11-item-schema.md` §1 (metadata rows, then Skip when / Test / How / Proof /
   Escalation / Ruled out when and Record), takes the next free id in its chapter, and uses verified identifiers
   only: every MASTG, MASWE, CWE or VRT id exists in `data/standards-index.csv` or `data/vrt.csv` — never invent
   one. Commands run on a stock Linux or macOS harness; decompiled paths use `$DEC`.
3. Generalise: describe the mechanism, never the engagement (lint fails on `SANE_LINT_TARGET_NAMES`).
4. `python3 scripts/build-checklist.py && python3 scripts/lint-checklist.py` — zero errors, and no new warning
   from the lines you wrote.

## /chapter-audit — reviewer or adversarial verifier of one chapter

Reviewer: start from `python3 scripts/lint-checklist.py 2>&1 | grep "checklist/Dnn"` and
`python3 scripts/item.py --domain Dnn`, then read every item against `docs/11` (§1 item shape, §2 chapter shape,
§3 severity, §4 `Requires` tags, §5 `Record`, §6 rules). Each defect once, in the `docs/08` §4 shape: item (or
`chapter`), field, rule, tier (error / warning / by-hand), the defect in one sentence, the evidence quoted, the
impact for a model operator, the concrete fix. A fact you cannot check offline is a hypothesis (with how to check
it), not a defect. Verifier: try to refute each defect against the current text — refuted when the quoted evidence is absent,
the text already meets `docs/11`, the rule is misapplied, or the fix would make the item wrong. Audit mode edits nothing unless the brief says to apply fixes; when the brief
supplies a return schema, fill it from the same facts.

## Hard limits

No engagement access, no target, no device, no network test. Nothing fabricated — an identifier you cannot find in
`data/` is not cited. No `git commit`, no `git push`: the coordinator commits on a branch and opens the
Checklist-gap issue.

## Return

```text
Authorisation: <the line>
CHANGED: <file> · <item ids> · correction | addition          (gap)
BUILD/LINT: <errors> errors · <warnings> warnings (new: <lines>)
ISSUE: <title> + the fields of .github/ISSUE_TEMPLATE/04-checklist-gap.yml (kind, domain, existing, severity, attacker, applies, requires, test, how, proof, escalation, ruled_out, evidence)
DEFECTS: <item | chapter> · <field> · <rule> · <tier> · <defect> · "<evidence quoted>" · <impact> · <fix>   (audit)
HYPOTHESES: <item> · <claim> · <how to check>                                                            (audit)
```
